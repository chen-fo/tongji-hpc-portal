# Phase 4：任务观察、预算与内部计费初版

本阶段提供 Slurm 任务的后台只读查询、人工归属、预算提醒和内部费用核算。系统没有预置真实费率或接入学校账单接口，实际费用以学校账单为准。当前不支持网页提交或取消作业，不会强制限制终端提交；预算只用于观察和提醒。

2026-10-29 在一个同济 Intel 官方账号上只读探测，`squeue`、`scontrol` 和 `sacct` 查询均成功，集群为 `paracloud`，Slurm 版本为 22.05.10。默认查询范围内实时队列及历史记录均为空，因此尚未验证真实任务的时间、资源、状态和费用，也不能据此推断更早的记录是否存在。探测没有提供 `Restarts` 字段；目前系统不会假设任务未重排队，真实任务因缺少该证据可能保持“待核算”，需人工核实。该结果只适用于本次测试账号和当时的服务器配置。

## 升级与启动

已有数据库先备份，再在 `backend/` 执行迁移并重启后端，具体命令见 [README](../README.md)。迁移保留现有用户和历史数据。服务继续使用已有的 Mock 或真实 SSH 配置；真实密码仅在本机终端隐藏输入，或通过已配置的密钥、ssh-agent、Keychain 获取，不应写入源码、配置或日志。真实 SSH 仍须验证主机密钥。

后端启动后会为启用的官方账号定期查询 `squeue` 和 `sacct`，并使用 `scontrol` 确认集群信息；不提交、取消或修改 Slurm 作业。Mock 默认没有预置任务，空列表不表示真实集群没有任务。一个账号的查询失败不会删除已有缓存，也不应影响终端和文件功能。

默认每 30 秒同步一次，首次历史查询回溯 30 天，此后每小时至少进行一次同样范围的回扫，补查延迟出现的记账记录。默认值可在本地配置中调整：`PORTAL_SLURM_SYNC_INTERVAL_SECONDS`、`PORTAL_SLURM_INITIAL_LOOKBACK_DAYS`、`PORTAL_SLURM_FULL_HISTORY_INTERVAL_SECONDS` 和 `PORTAL_SLURM_MAX_RECORDS`。回扫失败、历史不可用或记录无法解析时不推进完整回扫水位，保留缓存并在页面提示。已观察到但终态未确认的任务会根据其提交时间扩大后续查询范围。

30 天是默认查询范围，不保证捕获范围外、从未观察到的任务；查询结果过多或服务器不支持所需字段、权限时可能不完整。重启后继续根据数据库中的同步记录补查；超过历史保存期的服务器记录无法由平台找回。页面显示最近成功同步时间、过期或部分同步状态，请结合这些信息判断数据是否完整。查询时间统一处理为 UTC，网页以北京时间显示；服务器的具体行为仍需真实联调确认。

## 本机只读探测

先确认本地已配置所需官方账号、SSH 主机密钥和连接参数，再在 Mac 的交互终端运行：

```sh
/bin/bash /Users/chenfk1/Projects/Serve/.tools/run-slurm-readonly-probe.sh
```

脚本当前固定探测数据库中的官方账号 ID `1`，会提示在本机隐藏输入 HPC 密码，且只在进程内存中使用。它检查 Slurm 命令、集群、支持的历史字段、时区和只读查询结果数量，不提交或取消作业，不输出作业脚本或环境变量。报告保存在本机 `.tools/` 下脚本打印的路径；执行前请确认账号 ID `1` 就是要测试的账号。若使用其他账号或密钥认证，可在 `backend/` 运行 `uv run python -m app.cli probe-slurm --help` 查看参数。请勿将密码发送到聊天中。

## 任务与归属

管理员在“任务”查看各官方账号的队列与历史记录；成员只看到已确认归属于自己的任务。任务显示实际开始、结束时间和调度器预计时间，预计时间不代表已发生。任务从队列消失但尚无可信终态时显示“状态待核实”，不会凭空推定已结束。查询失败或数据不完整时应等待补查并核对服务器信息。

外部提交的作业默认未归属，系统不根据目录或名称猜测用户。管理员核实证据后，在任务行点击“确认归属”，选择绑定同一个官方账号的成员并填写原因。该操作记录操作者、用户和原因，已确认的归属不能直接覆盖；成员无法查看其他人的任务或自行认领。共享官方 Linux 账号本身并不提供成员间的 Linux 权限隔离。

## 费率、预算和费用

1. 管理员在“费用与预算管理 → 用户预算”设置每位成员的累计预算及提醒阈值，并填写原因。预算不会自动按月清零或预留作业费用。
2. 在“计价表”新增费率版本。先向学校核实对应集群、分区、计费单位、CPU 物理核与 Slurm CPU 的换算、GPU 型号及其单价、GPU 作业是否另计 CPU，以及分配资源是否覆盖所有计费资源。填写来源网址、核实日期和生效时间并确认；不确定的规则不要猜测。每个版本独立保存，新版本不会改写已入账费用。
3. 在任务的“查看费用”中查看估算或待核算原因。仅在归属、时间、资源及费率等数据足够可靠时提供估算；复杂、重排队、挂起、资源不完整或跨费率变更等任务可能需要人工核算。运行中估算基于最近同步的记录，并非最终费用。
4. 管理员可对满足条件且有 `sacct` 最终状态和结束时间的任务点击“确认记入费用”。系统只为同一任务记账一次，并冻结入账时的任务数据、费率版本、金额和舍入依据；如果后续调度数据发生变化，会提示人工核对，不会静默改写已有流水。费用使用人民币，资源金额合计后四舍五入到分。
5. 在“费用与预算管理 → 用户预算”可登记手工调整或学校账单差额；须填写原因，学校账单差额还须填写账单参考号。流水记录操作和来源，调整不会覆盖原流水。当前没有自动获取学校账单或自动完成对账。

学生可在“费用与预算”查看自己的预算、已记账金额和流水；管理员可查看所有成员。提醒基于已记账金额，未核算任务不包含在其中。由于尚无作业预留功能，汇总中的预留、可用额度和运行中估算暂不可用；单个任务的估算可在任务详情中查看。未归属任务、存储费用及其他未核实的共享费用不会自动分摊。
